| 项 | 说明 |

## 1. 测试用例

> 判定列统一用 **✅ 通过 / ❌ 失败**。遇到 ❌ 先看「排查」列，修好后再继续。

### C1 App 启动与后端拉起
- **前置**：无
- **操作**：双击启动 `Deepseek Science.app`
- **预期**：
  - 窗口正常打开（DeepSeek 蓝风格、左侧项目列表、右侧工作台）
  - 首页能显示默认项目与历史会话（若有）
  - 终端无报错；`lsof -i :17896` 能看到 `dss-backend` 监听
- **判定**：窗口打开 + 后端监听即 ✅
- **排查**：窗口空白 → 看 backend.log；端口被占 → 壳会自动换端口，无需处理

### C2 新会话第一轮对话（缓存计量显示）
- **前置**：C1 通过；已配 key
- **操作**：新建会话 → 输入「用一句话说明质数有无穷多个」→ 发送
- **预期**：
  - thinking 折叠块（若有）→ 正文打字机式输出 → complete 后底部出现 usage 行
  - usage 行格式：`tokens: ~2575 in / ~144 out · cache 99% (2560h/15m)`
  - **cache 百分比通常 ≥ 90%**（system 前缀 + 工具 schema 被 DeepSeek 公共前缀检测落盘命中）
  - `h + m ≈ in`（命中+未命中约等于输入 token）
- **判定**：usage 行出现且带 `cache xx% (Nh/Mm)` 即 ✅（**这是本次改动「缓存计量」的核心验证**）
- **排查**：无 cache 字样 → 后端是旧版本（需用 83fe72f 构建的 .app）；usage 行都没有 → 看 /logs 页或 backend.log

### C3 同会话第二轮（前缀稳定命中）
- **前置**：C2 完成（同一会话）
- **操作**：继续输入「那哥德巴赫猜想和它有什么关系？简单说说」→ 发送
- **预期**：
  - 本轮 `cache` 百分比仍 ≥ 90%（历史 + system 前缀稳定命中）
  - `m`（未命中）只增长本轮新内容（新用户消息 + 新回复）的量级，`h` 覆盖历史
- **判定**：命中率稳定在 90%+ 即 ✅（**「稳定前缀」的直观证据**；自动化实测 98.3%）
- **排查**：命中率骤降 → 检查是否切换了模型/修改了 Settings（会清缓存，属预期）；否则看 backend.log 有无异常

### C4 工具调用多轮（真实科研场景）
- **前置**：C3 完成
- **操作**：输入「写一个 Python 脚本计算 2^10，并执行它」→ 发送，观察多轮工具循环（write_file → python → …）
- **预期**：
  - 工具调用卡片正常显示（ToolCallCard）
  - 每轮迭代后 usage 行的 cache 百分比维持高位（工具结果虽大，但历史部分命中）
  - 最终 natural 完成
- **判定**：多轮工具循环 + 命中率维持即 ✅
- **排查**：工具卡住 → 看 backend.log 的工具调用记录

### C5 长对话触发上下文压缩（压缩顺序回归）
- **前置**：同一会话已有多轮对话（C2–C4）
- **操作**：继续多轮长对话（或输入超长材料，如贴一段长文本让它分析），累计输入 token 接近窗口的 75%
- **预期**：
  - 对话不中断、不报「上下文压缩后仍超硬墙」
  - 后端日志出现 `rolling compact applied L1 fold(s)`（或 /logs 页 compact 记录）
  - 压缩后对话继续，历史关键信息仍在（模型记得早前讨论）
- **判定**：长对话能继续 + 日志有 compact 记录即 ✅（**本次「免费减负先行」不应让压缩行为变差**；自动化已证明免费 microcompact 可避免无谓的付费折叠）
- **排查**：报硬墙错误 → 提交后端日志

### C6 会话恢复（重启不丢）
- **前置**：C4 完成
- **操作**：退出 app（⌘Q）→ 重新启动 → 打开同一会话
- **预期**：
  - 历史消息完整恢复（含工具调用与 usage 行）
  - 继续对话正常
- **判定**：历史完整 + 可继续即 ✅

### C7 记忆召回（记忆块位置回归）
- **前置**：C6 完成
- **操作**：发一条明确事实（如「我偏好用 Python 和 numpy 做统计分析」）→ 等待 → 新建另一个会话 → 输入「请用 numpy 做统计分析」
- **预期**：
  - 新会话的请求里带 `[Memory]` 记忆块（可在 backend.log 或 /logs 观察；记忆是 harness-notice，不出现在用户可见 transcript）
  - 模型回答体现该偏好
- **判定**：新会话能利用记忆即 ✅（**记忆块移到视图末尾后功能不变**）
- **排查**：无记忆召回 → 确认 Settings 里 memory 开启；记忆抽取是后台 fire-and-forget，稍等再试

### C8 Plan 模式
- **前置**：无
- **操作**：发起任务时勾选/启用 plan 模式（或用含「先制定计划」的 prompt）→ 观察 generate_plan → 批准 → 执行
- **预期**：计划生成 → 等待批准（AwaitingPlanApproval）→ 批准后按计划执行 → 完成
- **判定**：plan 闭环正常即 ✅

### C9 取消 / 停止
- **前置**：任意长任务
- **操作**：对话进行中点停止
- **预期**：本轮停止，会话可继续新对话，无进程残留
- **判定**：停止干净即 ✅

### C10 模型/设置切换后的缓存失效（预期行为）
- **前置**：C2 完成
- **操作**：在 Settings 切换模型（或修改其它影响请求的设置）→ 再发一条
- **预期**：
  - 切换后第一轮 `cache` 百分比可能明显下降（前缀变了，缓存失效）——**这是 DeepSeek 缓存机制的预期行为，不是 bug**
  - 连续几轮后命中率重新爬升
- **判定**：理解「切换=缓存失效、随后恢复」即 ✅

### C11 日志页
- **前置**：任意测试后
- **操作**：打开 `/logs` 页
- **预期**：能按会话过滤；`llm_call` 记录包含 token/模型信息
- **判定**：日志可见即 ✅
